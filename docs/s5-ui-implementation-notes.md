# S5 UI 实施说明：模板、持久化数据与后续 GitHub 构建

日期：2026-10-26。本文记录 S5 的界面实现规则与 S6 接续设计。S4 本地真实网络及浏览器路径已验证；S5 模板、卷、数据库、连接与手工记录界面已接入真实 API，受控浏览器和真实本地浏览器流程均通过，见 [S5 验收](acceptance/S5.md)。S6 已开始实施，尚未验收，不能将其下述设计说明当作可用功能。

依据：[PRD F18–F22](prd.md#54-数据模板与-git)、[技术方案 3.5](technical-plan.md#35-存储日志与凭证)、[开发计划 S5/S6](development-plan.md#8-s5持久化数据库与基础模板)和[已确认 Stitch 映射](../designs/console-v2/stitch-screen-map.md)。

开发计划将这些能力分为两个连续阶段：

| 阶段 | 本阶段最小完整范围                                                                                                       | 后续范围                                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| S5   | Docker、Node.js 示例、静态站点、PostgreSQL、Redis 五类单服务模板；卷与挂载；同环境数据库连接；手工备份恢复指引和记录     | Node.js/静态模板使用可运行的预构建示例镜像                         |
| S6   | GitHub 授权、仓库/分支、固定 commit、显式 Dockerfile/构建上下文；隔离构建、Registry 推送、统一发布；Webhook 与待发布提交 | 免 Dockerfile、Monorepo watch paths、组合模板和通用变量引用属于 S7 |
| S8   | 平台内备份/恢复任务、计划与自动异地上传；自定义域名、Cloudflare、公网 TCP                                                | S5 的手工恢复验证仍是前置要求                                      |

S5 的设计入口为 B01/B05 → C02/C03 → E03；P0 手工备份记录参考 E04 的 `manual-records`。S6 接续 G04 → B03 → C03 → F01/F04/F06 → E01。F07 交互终端、B04 自动构建扩展和 E05/E06 完整平台恢复流程按各自阶段实施。

## S5 最小完整流程

1. **选择项目、环境与模板。** 从项目“添加服务”进入五类模板目录，持续展示 Project → Environment → Cluster。全局模板入口先选项目与环境，集群由项目继承。模板列表提供名称、用途、固定版本、资源及持久化要求；不会带入演示项目、默认数据库或另一集群的端口。
2. **填写参数并审阅生成配置。** 参数由受控 schema 提供，展示镜像版本、具名端口、资源、探针和卷请求。数据库模板同时说明单实例、私有访问、凭证生成与持久化策略。预览返回统一服务配置和具体阻止原因，保存后进入现有发布预览。
3. **保存草稿，再发布。** 保存不创建健康实例。发布固定服务 revision、模板版本、镜像和卷引用，通过统一 Deployment/Operation 执行。页面分别展示草稿、已发布快照和当前观察。Node.js/静态示例仍属于镜像发布，构建日志显示不适用。
4. **观察持久化与连接应用。** 服务“数据与存储”展示申请容量、PVC/PV、StorageClass、回收策略、实际节点、实际挂载和观察时间。数据库展示非敏感私有地址、端口、库名与凭证引用；选择同项目、同环境的应用生成连接配置草稿，审阅并发布该应用后才生效。
5. **停止、恢复、删除并保留数据。** 沿用服务任务操作。停止与删除服务保留卷；删除审查列出将保留的具体卷。卷的销毁是独立操作，服务期望配置仍引用、实际 Pod 仍挂载或观察不足时，显示后端给出的阻止原因。确认页说明实际回收策略及数据删除后果。
6. **完成手工备份与恢复记录。** 指引明确源数据库/卷、备份格式、版本、校验和、数据时间点和离机副本位置。恢复先选择目标项目与环境，在其继承集群创建新服务/新卷，验证数据或文件后记录结果。原服务继续保留；数据恢复不自动切换 DNS 或迁移项目。人工填写“已执行”与平台实际核验结果应分别标注。

普通应用挂载可写本地卷时，页面说明单写入服务、单副本及 Recreate 带来的发布中断。数据库使用单实例 StatefulSet；Redis 模板明确启用 AOF。`WaitForFirstConsumer` 尚未绑定时，节点显示“等待首次使用后确认”。local-path 的申请容量不构成写入硬配额；节点剩余空间只能显示实际采集值与时间。

数据库首次初始化后，普通配置表单明确显示密码和主版本的保护状态。后端在保存、发布、重试及后续回滚中执行相同规则，UI 不提供通过修改镜像标签或初始化环境变量绕过保护的入口。独立维护流程属于 F48。

## S6 接续的 GitHub 最小完整流程

1. **分别准备三项集成。** G04 展示 GitHub 授权与仓库权限、Registry 推送/运行拉取条件、隔离 Builder 的可用性及各自检查时间。每项单独给出错误与重验入口。GitHub 授权通过不等于构建或镜像拉取可用。
2. **创建 Git 服务来源。** B03 只列出已授权仓库与分支，配置仓库内的 Dockerfile 路径和构建上下文。来源预览展示服务所属项目、环境、继承集群及将固定的 commit。保存来源与开始构建/发布分开，不能将当时的分支名当作不可变版本。
3. **跟踪统一发布过程。** 审阅后创建持久部署，展示固定 commit、构建、推送、镜像 digest/架构、配置应用和健康检查。构建失败定位到构建阶段；推送成功也不能标记服务已经运行。任务完成后进入服务观察与 S4 域名独立检查。
4. **接收真实推送。** Webhook 详情区分接收事件和每个匹配服务的投递，展示拒绝、重复、忽略、待发布、已排队或失败的实际原因。重复事件不重复发布，同一合法事件投向多个服务时，各自结果可追踪。
5. **保持停止语义。** stopped 服务的合法推送只留下待发布提交。服务页面并列提供“恢复原已发布版本”和“审阅并发布所选提交”；恢复不会消费待发布提交。显式发布并启动继续沿用现有确认与服务活动任务槽。
6. **按原来源重试。** 原构建已有产物时，重试显示并复用原 digest；产物不可用时明确失败。只有尚无产物的原任务才按原 commit 与配置重新构建，执行时使用当前有效认证。不能悄悄改用 HEAD、latest 或当前草稿。

构建秘密只通过专用凭证引用进入隔离执行环境。普通详情、预览、复制动作和日志不返回 Git Token、Registry 密码或构建秘密。构建与运行拉取凭证分别展示用途；控制面不是源码构建机。

## 公开 Interface 与后续扩展

以下按领域说明前后端使用的数据与行为。S5 的精确路径和字段已维护在 [API 契约](api-contract-s5.md)、DTO/OpenAPI 与生成客户端；GitHub/Builder/Webhook 属于 S6，实施时另补公开契约。Console 不导入 Prisma 或后端凭证代码。

| Module                    | 调用方需要知道的 Interface                                                                                                                  | 保持在后端的 Implementation                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 模板目录与预览            | 稳定模板 ID/版本、有限参数 schema、镜像与架构要求、生成的完整服务配置、卷/数据库需求、可显示的校验问题                                      | 模板解析、参数限制、固定镜像、配置生成及目标校验                 |
| 卷与挂载                  | Volume ID、归属环境、实际集群、PVC/PV/StorageClass、申请容量、配额支持、节点约束、回收策略、期望与实际挂载、观察时间/过期标记、销毁阻止原因 | 归属验证、单写入策略、挂载互斥、资源 UID/版本核对和删除确认      |
| 数据库                    | 数据库 ID、引擎/主版本、初始化状态、受保护字段说明、卷引用、非敏感连接信息、运行期凭证引用、应用依赖及观察结果                              | 凭证生成、初始化识别、跨入口变更保护和统一 StatefulSet 发布      |
| 数据库连接预览            | 消费应用身份/revision、同环境的可选数据库、输出变量名称与引用、配置差异、依赖就绪问题；保存返回明确的草稿结果                               | 稳定依赖绑定、项目/环境/集群核对、秘密版本固定及发布前依赖检查   |
| 手工备份/恢复记录         | 源与新目标身份、数据时间点、格式/版本、校验和、离机副本位置、执行与验证状态/来源、失败说明                                                  | 实际导出/导入步骤与兼容验证由 S5 runbook 负责；平台化任务另属 S8 |
| Git/Registry/Builder 集成 | 脱敏引用、授权范围、仓库/分支分页、分项检查结果/时间、权限或到期问题                                                                        | 当前认证解析、外部协议、凭证隔离与执行器连接                     |
| Git 来源与构建            | 服务来源判别、仓库身份、分支、固定 commit、Dockerfile/上下文、来源 revision、构建产物 digest/平台、阶段与错误、有限日志契约                 | 原始请求体验签、事件去重、目标投递、检出/构建/推送和任务恢复     |
| 待发布提交                | 接收事件与服务投递的稳定 ID、commit、来源 revision、原因、关联任务、可执行动作与阻止原因                                                    | stopped 判断、每服务幂等、串行任务和不可变发布来源               |

元数据修改沿用 revision 和 Problem Details；触及运行面的变更返回持久 Operation/Deployment，并带可导航的稳定资源身份。相同意图的传输重试复用幂等键；受理结果不替代运行状态。列表筛选覆盖完整查询范围并使用 cursor 分页。权限、范围、未知观察和在途任务的限制必须由后端再次核对。

S5 任务与观察 DTO 已支持 StatefulSet 和 PVC/PV；Git 构建来源在 S6 扩展。展示层按照明确的资源/来源判别字段选择文案，不能只检查 `action`、`target` 等多个任务共用的属性。这一点已在 S4 域名任务接入旧服务任务页时出现，后续继续保持明确判别。

## 实施顺序与最小验收

S5 按卷/数据库/模板契约，完成模板目录与参数 → 卷挂载和数据观察 → 数据库连接草稿 → 删除留卷与独立销毁 → 手工记录与恢复验证。S6 在这些能力上增加集成设置 → Git 来源 → 构建/推送阶段 → 待发布提交与 Webhook 结果 → 域名访问联动。真实云入口尚未就绪时继续独立本地工程，依赖模拟结果和本地结果分别记录，不据此宣称公网关口通过。

验收至少保留下列证据：

- 五类模板真实保存、发布并运行；Node.js/静态示例来源明确。PostgreSQL 写入行、Redis 写入键后分别重建 Pod，验证数据仍在。
- 卷绑定前节点未知、绑定后节点/PVC 真实可见；跨环境挂载、多写入、使用中销毁被拒；停止/删除服务后卷保留；普通保存和重试不能绕过数据库密码/主版本保护。
- 同环境应用连接数据库成功；其他环境不会自动获得连接引用或公网入口。配置注入保存后仍等待应用发布。
- PostgreSQL、Redis 和普通卷各有恢复到新目标的真实数据/文件验证，记录可恢复的数据时间点、恢复耗时和至少一份离机副本。
- GitHub 真实 push → 固定 commit → 隔离构建 → 推送 digest → 发布 → HTTPS 访问；伪造、重复、非目标分支、多服务投递和 stopped 推送分别验证，构建失败保留日志和原来源。
- 新表面覆盖明暗主题、1440/1024/390、键盘与中文组合输入、版本冲突、恢复只读、请求中离页与迟到响应。受控界面证据和真实 API/运行面证据分别记录，最终进入对应阶段验收文档。
