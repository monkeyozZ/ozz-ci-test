### 4.1 S1 的设计系统与体验交付

S1.07 分为三个可检查的交付部分，保留原任务 ID；设计系统落地与浏览器体验验收计入 S1，不留到 S9 才开始。Stitch 全产品设计已经交付，S1 应用实施按以下范围验证。

1. **设计基线**：完整 Stitch UI 与交互设计覆盖全产品页面及状态；S1 应用实现先落地登录、项目列表/创建/详情和服务器/集群登记。统一明暗 tokens、中文/等宽排版、组件尺寸及状态规范，记录来源版本与本地修改，验证桌面和窄屏布局。原型可以提前展示后续能力，应用中尚未实现的能力不能冒充已可用功能。
2. **交互组合**：导航以项目为主入口，创建项目选择一个 Cluster，项目内切换环境并管理服务，目标集群持续显示且只读继承；全局服务页是聚合入口，全局创建动作先确定项目/环境。完成上下文与 URL、列表/表单、查询缓存和状态反馈，区分首次加载与后台更新；基础设施页面不附加虚假的全局 production 环境。命令面板仅索引当前可用、已授权的资源与动作，明确搜索范围，不引入额外全局搜索服务。
3. **质量验收**：浏览器完成实际 CRUD 与诊断任务；检查主题、焦点恢复、中文 IME、未保存编辑、迟到请求和 1440/1024/390 CSS px、200% 缩放。建立有代表性的截图基线和交互测试，截图不能替代真实行为验收。

后续 S3 的服务列表、三类配置/运行状态与日志，S7 的编辑器/终端，S8 的图表沿用这些组件和规范。每阶段完成对应 UX 行，再在 G-MVP/S9 联合回归；不能只换组件库名称后宣称体验完成。

## 16. 性能、容量与可用性验证

性能阈值、恢复目标和数据保留要求以 PRD 的 N03/N04 为准，以下定义对应执行方法，不把规划规格当作最大容量保证。

1. **S1 基线**：记录本机版本、数据库/Redis 配置、API 查询与写入的 p50/p95、CPU/RSS、连接池和页面操作结果。
2. **G-MVP 目标机基线**：参考 2 核/12 GB/80 GB 独立控制面，在固定的 100 个服务元数据、1 万条部署历史数据集上，以 5 个并发管理请求、2 个有输出上限的日志窗口连续运行 10 分钟。PostgreSQL 可用时，元数据/缓存查询 API 和异步任务接收 API 的服务器侧 p95 目标均不超过 1 秒；分别测正常、单集群超时和 Redis 不可用场景。该指标不包含 SSH/构建/rollout 的外部耗时及客户端公网 RTT。另完成至少两个独立真实集群的功能测试，元数据样本不能证明 100 个真实服务的承载能力。
3. **容量增长**：测部署/Operation/Outbox 记录和任务日志的日增长、保留清理后的占用；检查 PostgreSQL 临时文件、Docker 日志及备份临时空间，避免多个独立上限合计超过磁盘预算。
4. **竞争隔离**：外部构建/备份执行期间，确认控制面查询和其他集群观察仍满足 PRD 目标；单个集群故障不能耗尽所有同步并发。
5. **恢复与持续运行**：G-MVP 完成控制面与 PostgreSQL/Redis 应用数据的手动恢复并记录实测 RPO/RTO，不承诺 HA；旧控制面备份先进入恢复锁和只读对账。S9 运行包含定时采集/清理/通知/备份的持续观测测试，至少跨越两个默认备份调度时点，并记录积压、句柄和内存增长。P1 默认每日 03:00（Asia/Shanghai），保留 7 份成功备份；配置可调整但受存储配额限制，成功备份间隔目标不超过 24 小时，失败或陈旧触发告警。
6. **浏览器体验**：使用 ENV-UI 与 PRD 8.3 的相同数据规模，记录真实交互会话、冷/热缓存与包体；本地反馈目标 100ms 内、INP≤200ms、CLS≤0.1。两个日志窗口各以 1 万行或 5 MiB 上限持续追加 10 分钟，检查输入/滚动及内存回收。延迟、接口等待和外部任务耗时分开归因；目标未达时保留失败，不用后端压测替代浏览器证据。

任务与采样采用 PRD 的初始可配置值，并在对应阶段验证超时行为：

| 操作                | 初始值与验收                                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| SSH 建连/只读预检   | 10 秒/60 秒，S2 验证连接与预检失败分别定位                                                              |
| 单次 Kubernetes API | 15 秒，S2/S3 验证超时不会占满全部观察并发                                                               |
| K3s 初始化          | 总上限 15 分钟，超时保存已发生动作，不自动重装                                                          |
| 发布健康等待/构建   | 5 分钟/15 分钟，可按服务调整；S3/S6 验证持久错误和取消结果                                              |
| 状态观察            | 活跃发布约 15 秒、集群约 30 秒；正常常规变化目标 60 秒内可见，连续失败或距成功观察超过 90 秒标过期/未知 |
| 重试                | 有上限指数退避，仅网络/429/可恢复外部故障；配置/认证/主机指纹错误不盲目重试                             |

RPO/RTO 使用恢复演练实际可恢复的数据时间点和完成恢复耗时计算。备份失败、备份陈旧或存储不可达时，应显示最后成功时间和风险，不因配置了“每日执行”就声称 RPO 仍满足目标。

未经实测，不承诺固定服务数量、零停机、全自动故障迁移或任意数据库恢复时间。若实际不满足目标，先降低并发/采样/保留成本或调整目标资源，再更新容量说明和验收，不隐藏失败。

## 17. 部署、升级与回退

### 17.1 控制面首次部署

S1 提供本地运行路径，G-MVP 前完成目标机部署验证。部署材料包括固定版本镜像、Compose、完整变量说明、受保护主密钥、管理员初始化方式、数据库迁移入口、Caddy 管理域名配置和持久目录。

先验证必要配置和依赖，再执行独立迁移步骤，随后启动 API/Worker/控制台并完成健康与登录检查。数据库和 Redis 只在控制面内部网络监听；公网管理入口必须是 HTTPS。业务镜像、源码构建和应用 PVC 留在外部运行面。

### 17.2 控制面升级流程

| 顺序 | 操作                                                                    | 验证/失败处理                                                                                                  |
| ---- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| U1   | 核对目标版本、兼容 schema、配置变更、磁盘余量和已有在途任务             | 不兼容或空间不足先阻止；必要时停止接收新变更，既有应用继续运行                                                 |
| U2   | 备份 PostgreSQL、配置、所需日志索引和对应主密钥版本；异机保存并验证可读 | 没有可用恢复材料时不执行破坏性迁移；数据库备份与密钥分别保护                                                   |
| U3   | 在预发布环境验证迁移；生产执行独立、可观察的迁移步骤                    | API 启动不自动清库或重置 schema；失败保留原版本和错误信息                                                      |
| U4   | 更新控制面镜像并恢复 API/Worker，处理未完成 Outbox/租约                 | 普通升级按真实状态收敛；若恢复过旧数据库备份，先维持恢复锁与只读对账，不能直接投递旧任务；不因重启重发全部应用 |
| U5   | 验证登录、凭证解密、集群观察、部署查询和一项低影响测试操作              | 结果不符时按兼容性选择应用镜像回退或数据恢复，记录差异                                                         |

尽量采用先扩展再收缩的 schema 迁移，明确旧/新代码可共存范围。降级镜像不代表数据库 schema 可逆；旧程序不兼容新 schema 时应拒绝启动。

从备份恢复不同于普通进程重启。恢复流程必须在 API/Worker 启动前启用恢复锁，管理写操作及旧 Outbox/任务投递暂停，仅允许只读观察。逐项比对资源标签、Kubernetes revision/实际配置、DB 快照和未知受管资源；Kubernetes 比备份新时不得根据旧 DB 自动删除、降级或覆盖。核对任务固化的执行目标与归属，已使用迁移功能时还须检查源/目标映射，不能读取当前 Project 目标重放旧任务。差异得到明确处理和确认后才释放恢复锁，随后恢复可确认安全的任务；原任务不能不经核对全部补发。

### 17.3 四类回退必须区分

| 类型           | 可用方式                                                                                                   | 不能承诺的内容                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 控制面程序回退 | schema 兼容时恢复上一版 API/Worker/Console 镜像和对应配置                                                  | 不自动撤销所有已发生的数据库迁移                                                            |
| 控制面数据恢复 | 从匹配的数据库+密钥/配置恢复并保留原 ID，启用恢复锁，先只读对账并暂停旧任务投递，确认后恢复写入            | 不将空数据库当恢复；不因旧备份删除/降级更高 revision 或未知资源；恢复点之后的变更需逐项处理 |
| 应用镜像回滚   | S7 在可信完整快照基准上换用历史成功 digest，创建新 Deployment 并验健康；配置不一致先对账                   | 不拼混合 Pod 配置；不回滚 PVC、数据库 schema 或秘密值；不能隐藏数据版本兼容问题             |
| 应用数据恢复   | 在明确的目标项目/环境及其继承集群，使用已校验备份恢复到新服务/卷，验证后明确切换；覆盖原目标需单独风险确认 | 不默认在线覆盖原库；不把配置复制当数据迁移或自动完成 DNS 切换                               |

K3s、Traefik、cert-manager 和存储组件升级属于运行面维护。分别核对兼容版本、在临时集群演练并确定维护影响，不能随控制面升级静默批量升级所有服务器。多节点排空也不能保证本地卷数据自动跟随。

这是 P2.03 的内部拆分，共用同一套平台 API、权限、审计和 AI 运行记录。提供方、模型及调用预算在 AI-A 前确定，文档容量与 embedding 配置在 AI-C 前确定；三项估算合计 24–41 人日，不计入 P0/P1，也不与 P2.03 重复加算。

## 22. 每阶段的交付记录格式

每个阶段完成后新增对应验收记录，至少包含：

1. 对应需求 ID、任务 ID、实际完成/未完成范围及变更文件清单。
2. 已锁定版本、迁移说明、配置变化、必要权限和受影响资源。
3. 实际可执行的安装/启动/迁移/管理员初始化/检查命令，以及运行所需前置条件；S1 命令已在开发说明中交付，后续阶段按实际产物追加。
4. 实际执行的测试、时间/环境、结果、失败原因和证据位置；未执行项明确标注。
5. 用户验收步骤、预期结果、测试数据和清理范围；涉及数据的操作说明备份与回退。
6. 资源/性能观测、已知限制、阻断问题，以及更新后的后续阶段估算。

只有达到本阶段退出条件才标为完成。任何失败、暂缺真实资源或需要兼容性复核的项，都在记录中保留；不能靠改文案、演示数据或降低验证范围把它变成已通过。
