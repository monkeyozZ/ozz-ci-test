个人版 Zeabur PaaS 平台 — 产品需求文档（PRD）

一、项目背景

我计划开发一个个人使用的轻量级 PaaS 平台，参考 Zeabur 的核心产品体验，用于统一管理自己的多台 VPS，并在平台中完成应用部署、域名管理、HTTPS 配置、日志查看、数据库管理等操作。

平台采用 K3s 作为容器编排底座，希望实现类似 Zeabur 的使用体验：

* 统一管理多台 VPS 和多个 Kubernetes 集群。
* 支持 Git 仓库和 Docker 镜像部署。
* 支持 Dockerfile 自动构建镜像。
* 支持应用自动分配二级域名和 HTTPS。
* 支持查看部署状态、构建日志和运行日志。
* 支持数据库、Redis 和持久化存储。
* 支持应用模板和 CLI。
* 尽可能通过 Web 控制台完成操作，减少手动 SSH 登录服务器的频率。

这是一个个人使用的自托管平台，不是面向公众的商业 SaaS。

二、项目目标

2.1 核心目标

第一阶段优先实现以下完整闭环：

1. 在控制台添加一台 VPS。
2. 通过 SSH 初始化服务器并安装或接入 K3s。
3. 在平台中注册并管理该 K3s 集群。
4. 创建项目和应用服务。
5. 部署现成的 Docker 镜像。
6. 查看应用运行状态及日志。
7. 为应用分配域名并自动配置 HTTPS。
8. 通过浏览器访问已部署的应用。

在以上功能稳定后，再逐步实现 Git 自动部署、Dockerfile 构建、数据库模板、持久化存储、CLI 和多集群管理。

2.2 非目标

第一版暂不实现：

* 多租户、公开用户注册和商业计费。
* 复杂的企业组织、团队角色和权限体系。
* 跨地域自动容灾和复杂的多云调度。
* 自研 Kubernetes、容器运行时或反向代理。
* 自研完整的日志、监控和证书签发系统。
* 复杂的自动扩缩容和自动故障迁移。

三、用户与使用场景

3.1 用户类型

第一版只有平台管理员，即我本人。

3.2 主要使用场景

1. 管理不同服务商、不同地区的 VPS。
2. 在 VPS 上运行自己的前端、后端、工具和 AI 应用。
3. 通过 Git 提交代码触发自动部署。
4. 直接部署已有的 Docker 镜像。
5. 为应用自动配置域名和 HTTPS。
6. 在统一控制台查看所有应用的状态、日志和资源占用。
7. 快速部署 PostgreSQL、Redis 等常用服务。
8. 通过模板快速创建新项目。

四、功能需求

优先级定义：

* P0：MVP 必须完成。
* P1：核心闭环完成后实现。
* P2：后续增强。

4.1 项目与服务管理

P0

* 创建、查看、编辑和删除项目。
* 一个项目可以包含多个服务。
* 创建和管理服务。
* 支持服务名称、服务类型、目标集群等基本配置。
* 支持区分 production、staging 等环境，初期可以只实现基础环境模型。
* 展示服务运行状态、访问域名、部署版本和最近一次部署时间。

P1

* 项目复制和导出。
* Monorepo 子目录部署。
* 多环境配置差异管理。

4.2 VPS 与集群管理

P0

* 添加、编辑和移除 VPS。
* 记录服务器名称、IP 地址、SSH 用户、端口、凭证引用和标签。
* 使用 SSH 执行服务器连通性检查。
* 检查操作系统、CPU、内存、磁盘及必要的网络端口。
* 支持安装 K3s 或接入已有 K3s 集群。
* 展示集群和节点的连接状态、Ready 状态及基础资源信息。
* 支持管理多个集群。
* 查看每个集群中运行的应用和工作负载。

P1

* 将新的 VPS 加入现有 K3s 集群。
* 节点排空、移除和重新加入。
* 节点异常告警。
* 节点资源历史趋势。

重要架构要求

平台必须区分 Server、Cluster 和 Kubernetes Node。

一台 VPS 不一定必须加入一个共享集群。平台需要支持管理多个相互独立的集群，以适应不同云服务商和不同地区的 VPS。

第一版优先完成多个独立集群的管理，再评估多节点共享集群。

4.3 应用部署

P0

* 支持部署现成的 Docker 镜像。
* 支持配置镜像地址、版本、容器端口和启动参数。
* 支持配置环境变量、资源限制和副本数量的基础设置。
* 将应用部署为 Kubernetes Deployment。
* 创建对应的 Kubernetes Service。
* 展示 Deployment、Pod 和 Service 状态。
* 支持重启、停止、删除和重新部署。
* 记录每次部署的状态、镜像版本、时间及失败原因。
* 支持部署状态轮询或实时更新。

P1

* 支持 Git 仓库部署。
* 支持 Git Webhook 自动触发部署。
* 支持 Dockerfile 构建。
* 支持镜像仓库推送和拉取。
* 支持部署历史、版本回滚和失败重试。
* 支持自定义构建命令及构建目录。

部署要求

部署必须采用异步任务模型，不能依赖一个长期阻塞的 HTTP 请求。

每次部署都必须有独立的 Deployment Record，并具备明确的状态流转，例如：

queued → building → deploying → waiting_healthy → succeeded

同时支持 failed 和 cancelled 状态。

应记录阶段时间、错误信息和日志位置。

镜像发布应尽可能使用不可变 digest，避免仅通过 latest 标签追踪版本。

4.4 域名与 HTTPS

P0

* 支持配置平台默认域名后缀，例如 apps.example.com。
* 支持为应用分配唯一的二级域名。
* 支持绑定应用与域名。
* 使用 Traefik 作为入口网关。
* 使用 Kubernetes Ingress 或 Traefik CRD 配置路由。
* 使用 cert-manager 管理 HTTPS 证书。
* 展示域名、路由和证书状态。
* 支持 HTTP 到 HTTPS 跳转。

P1

* 支持绑定自定义域名。
* 支持多个域名绑定同一个应用。
* 接入 Cloudflare DNS API。
* 支持域名解绑和证书状态排查。
* 支持私有服务及内网访问。

重要说明

域名系统必须区分 DNS 解析、网关路由和证书签发。

通配符 DNS 只能将域名解析到入口 IP，不能替代路由配置和证书管理。

默认域名需要在平台中持久化记录，并保证生成的域名唯一。

HTTPS 必须具备证书申请失败、续期失败和 DNS 配置错误的可观测性。

4.5 日志与监控

P0

* 查看应用 Pod 的标准输出和错误日志。
* 查看最近一次构建日志。
* 查看部署过程和错误详情。
* 查看应用运行状态和 Pod 重启次数。
* 查看节点 CPU、内存和磁盘的基础指标。
* 支持日志分页或持续刷新。
* 支持按服务和部署记录定位日志。

P1

* 支持日志搜索、过滤和下载。
* 支持资源阈值告警。
* 支持 Prometheus 指标采集。
* 支持日志集中存储。
* 支持历史资源趋势。

技术原则

第一版优先利用 Kubernetes API 和节点指标采集能力。

只有在确实需要集中检索或长期保存日志时，再引入 Loki 等组件，不要一开始过度建设监控系统。

4.6 数据库与持久化存储

P0

* 支持创建和管理持久化卷。
* 支持配置挂载路径和容量。
* 支持通过模板部署 PostgreSQL 和 Redis。
* 展示数据库服务状态。
* 提供数据库连接信息和环境变量注入。
* 支持敏感连接参数的安全管理。

P1

* 支持手动备份与恢复。
* 支持定时备份。
* 支持备份下载及远端对象存储。
* 支持数据库资源监控。

重要约束

第一版可以使用 K3s 的本地持久化卷方案，但必须明确数据所在节点和迁移限制。

不能假设 Kubernetes 能自动将本地磁盘数据迁移到其他节点。

需要在界面中明确展示持久化卷状态和数据风险。

4.7 模板系统

P0

* 提供基础 Docker 镜像部署模板。
* 提供 Node.js 应用和静态网站等基础模板。
* 支持模板参数和环境变量。
* 支持通过模板创建服务。

P1

* PostgreSQL、Redis 等模板。
* 支持自定义模板仓库。
* 支持模板版本。
* 支持一键部署。

模板必须使用统一的部署引擎，不要为每一种模板单独实现一套部署逻辑。

4.8 CLI

P1

设计平台 CLI，支持：

* 登录和配置平台地址。
* 查看项目、服务和集群。
* 创建部署任务。
* 查看部署状态。
* 查看应用日志。
* 重启服务。

CLI 通过平台 API 工作，不应默认要求用户直接访问 Kubernetes API。

五、技术架构建议

以下技术栈为初始建议，实施前可以根据项目复杂度和现有生态进行调整。

5.1 前端

* Vue 3
* TypeScript
* Vite
* Pinia
* Vue Router
* 选择一种成熟的 Vue UI 组件库

前端负责控制台交互、表单、状态展示、日志展示和资源管理。

5.2 后端

* NestJS
* TypeScript
* Prisma
* PostgreSQL
* Redis
* BullMQ

NestJS 负责业务 API、服务器注册、集群管理、部署任务、Webhook 和状态同步。

BullMQ 负责异步执行构建、部署和服务器初始化等耗时任务。

5.3 运行环境

* K3s：容器编排。
* Kubernetes API：管理应用工作负载。
* Traefik：入口网关。
* cert-manager：TLS 证书管理。
* BuildKit：Dockerfile 镜像构建。
* Prometheus：后续指标采集。
* Loki：后续集中日志。

控制面第一版可以通过 Docker Compose 运行在一台独立管理 VPS 上，应用则部署在受管理的 K3s 集群中。

5.4 控制面与运行面的边界

控制面负责：

* 项目、服务和部署记录。
* VPS 与集群元数据。
* 用户操作和任务调度。
* Git 授权及 Webhook。
* 域名与证书配置。
* 状态同步、日志聚合和错误处理。

K3s 运行面负责：

* 应用容器运行。
* Pod 调度和重启。
* Kubernetes Service。
* Ingress 路由。
* 持久化卷。
* Kubernetes 原生健康检查。

平台不能只保存自己的业务状态，而忽略 Kubernetes 中的真实运行状态。

必须考虑平台数据库和 Kubernetes API 之间的短暂不一致，并提供周期性同步与重试机制。

六、核心数据模型

至少考虑以下实体：

* Project
* Environment
* Cluster
* Server
* Service
* Deployment
* Domain
* Volume
* DatabaseInstance
* Template
* SecretReference

基本关系：

* 一个 Project 包含多个 Service。
* 一个 Project 可以拥有多个 Environment。
* 一个 Service 可以拥有多条 Deployment 记录。
* 一个 Service 关联一个目标 Cluster，并可关联多个 Domain。
* 一个 Cluster 可以包含多个 Server 或 Kubernetes Node。
* 一个 Service 可以使用多个 Volume。
* 数据库也作为可部署服务管理，并额外保存数据库类型及连接配置引用。

敏感信息不得以明文形式写入日志、普通 API 响应或前端代码。

SSH 私钥、Git 凭证、数据库密码、DNS API Token 和 Kubernetes 凭证必须采用安全存储机制。

七、API 设计要求

请根据上述功能设计 RESTful API，统一错误格式、分页格式和状态码。

API 模块至少包含：

* /api/projects
* /api/environments
* /api/servers
* /api/clusters
* /api/services
* /api/deployments
* /api/domains
* /api/volumes
* /api/templates
* /api/webhooks

示例接口：

* POST /api/servers：添加服务器。
* POST /api/servers/:id/initialize：初始化服务器。
* GET /api/clusters：查询集群列表。
* POST /api/services/:id/deployments：创建部署任务。
* GET /api/deployments/:id：查询部署详情。
* GET /api/deployments/:id/logs：查询部署日志。
* POST /api/services/:id/restart：重启服务。

具体接口应由实际业务模型决定，不要为了符合示例而机械实现。

部署日志可以先采用轮询接口，后续再增加 SSE 或 WebSocket。

八、非功能需求

8.1 安全

* 敏感凭证必须加密存储。
* 不允许在前端暴露 SSH 私钥和集群管理员凭证。
* 所有管理操作必须经过后端鉴权。
* SSH 操作限制在必要的初始化和维护场景。
* 构建任务应与控制面隔离。
* 避免在日志中打印密码、Token 和 Secret。
* 删除服务器、集群、卷和数据库前需要明确风险提示。
* 防止 Webhook 被伪造和重复触发。

8.2 稳定性

* 部署任务可追踪、可重试。
* 任务失败时保留错误原因和日志。
* 服务状态以 Kubernetes 实际状态为依据。
* 控制面短暂不可用不应导致现有应用被主动停止。
* 对外部 API、SSH 和 Kubernetes 操作设置超时。
* 关键操作必须具备幂等性，避免重试创建重复资源。

8.3 可维护性

* 前后端模块边界清晰。
* 统一配置管理。
* 提供数据库迁移。
* 提供基础测试。
* 提供结构化日志。
* 提供开发环境和部署环境配置示例。
* 关键部署流程有明确的验收标准。

九、MVP 开发计划

第一阶段：项目基础

* 初始化前后端项目。
* 配置 PostgreSQL、Prisma 和 Redis。
* 实现基础控制台布局。
* 实现项目、服务器和集群的数据模型。
* 建立统一错误处理、配置和日志规范。

验收标准：可以启动整个开发环境，并通过前端和 API 管理基础数据。

第二阶段：K3s 集群管理

* 添加 VPS。
* 检查 SSH 连通性。
* 初始化或接入 K3s。
* 查询集群和节点状态。
* 保存集群凭证引用。
* 实现集群状态同步。

验收标准：控制台能够连接至少一个真实 K3s 集群，并展示节点状态。

第三阶段：Docker 镜像部署

* 创建服务。
* 输入镜像和端口配置。
* 创建 Deployment 和 Service。
* 查询 Pod 状态。
* 查看运行日志。
* 实现重启、停止和删除。

验收标准：能够通过控制台部署一个真实 Web 应用并访问。

第四阶段：Git 与构建

* Git 仓库授权。
* Webhook。
* 构建任务队列。
* BuildKit 构建和镜像推送。
* 发布状态与日志。
* 部署历史。

验收标准：提交代码后能够自动完成构建和部署。

第五阶段：域名与 HTTPS

* 配置默认域名后缀。
* 生成应用域名。
* 创建 Traefik 路由。
* 配置 cert-manager。
* 展示证书状态和失败原因。

验收标准：通过应用域名访问部署成功的 HTTPS 服务。

第六阶段：存储与模板

* 持久化卷。
* PostgreSQL、Redis 模板。
* 基础模板参数。
* 数据备份方案。
* CLI 的第一批命令。

验收标准：能够通过模板部署应用和数据库，并验证持久化数据在 Pod 重建后仍然存在。

十、验收原则

MVP 完成时至少满足：

1. 能添加和管理 VPS。
2. 能接入至少一个真实 K3s 集群。
3. 能部署一个 Docker 镜像。
4. 能查看 Pod 状态和运行日志。
5. 能为应用配置域名与 HTTPS。
6. 能通过 Git 提交触发自动部署。
7. 能部署带持久化卷的数据库服务。
8. 关键错误可定位，失败任务可重试。
9. 敏感凭证不会通过前端或日志泄露。
10. 提供清晰的安装、配置、开发和部署文档。

开发过程中遵守以下原则：

* 优先实现可以运行和验证的最小闭环。
* 不要一次性生成所有模块。
* 不要虚构已经完成的功能。
* 每个阶段结束后提供修改文件、启动命令、测试结果和验收步骤。

* 优先使用成熟的开源组件，不重复实现 Kubernetes 已有能力。
* 在开发前先检查当前仓库，保留已有有效代码和约定，避免不必要的重建。

请从需求分析与技术方案设计开始，不要直接进入完整代码实现。
