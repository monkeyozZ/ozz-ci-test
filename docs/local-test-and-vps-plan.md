# 本地测试与 VPS 准备

用户已确认暂时没有应用 VPS，先在本机开发和测试，之后再接入真实服务器；已授权停止本机与本项目无关的运行服务以释放资源。此调整改变测试资源的准备顺序，不将本地结果当作公网或 Oracle 实测。

## 先用本地资源推进

本机为 Apple M1 Pro、8 CPU、16 GiB 内存。2026-10-26 为减少多台测试 VM 同时运行时的交换压力，已在控制面备份、正常停机后，将 Docker Desktop 的内存分配从 8092 MiB 调整为 4096 MiB；原 PostgreSQL/Redis 容器恢复健康，全部 88 个容器、99 个卷、原磁盘与其他设置均核对保留。该调整只影响本地测试预算，不是远端容量实测。

2026-10-25 已停止 AppHub 的 5 个容器，保留原容器和 volumes：`apphub-local-check-web-1`、`apphub-local-check-api-1`、`apphub-local-check-parser-1`、`apphub-local-check-postgres-1`、`apphub-dev-postgres-1`。本次 Docker 重启后它们仍保持停止；以后恢复原项目可对这些名称执行 `docker start`。

| 测试层     | 本地实施方式                                                                 | 能证明的范围                                                                                |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| S1 控制面  | Node 24 API/Worker、生产 Console、真实 PostgreSQL/Redis；独立 Compose 部署栈 | 鉴权、CRUD、凭证、并发/故障、控制面恢复、界面行为                                           |
| 集群 API   | 两套相互独立的本地 K3s API，按需要运行                                       | 客户端隔离、导入、部署资源与多集群观察；不是 mock                                           |
| SSH 初始化 | 独立 Linux 虚拟机，固定 Ubuntu 24.04 与 K3s 版本                             | 主机指纹、预检、安装、重复安装保护与 SSH 超时；普通 k3d 容器不能替代 systemd/VPS 初始化验证 |
| 应用运行   | 本地测试应用、临时卷与数据库样本                                             | Deployment/Service/PVC、日志、错误恢复、应用数据恢复                                        |
| 入口和证书 | 本地路由/测试 CA；公网就绪后另验                                             | 本地 TLS 与反代；不证明真实 DNS、公开 ACME 或云防火墙                                       |

控制面与运行面仍分开；本地共用物理 Mac 只作为开发拓扑。先结束控制面镜像构建及性能采样，再启动集群测试，避免同时运行多个完整栈。集群镜像、版本、资源上限、专属网络/端口、密钥目录和启停命令必须随真实创建结果记录；不预先将尚未建立的环境写成可用。

本地 Linux ARM64 结果只代表已测架构。未来选择 x86_64 VPS 时补做该架构镜像与依赖验证。真实云网络、sudo/SSH 差异、磁盘性能、DNS、外部 Registry 和持续运行容量仍需要远端验收。

## 正式使用需要几台

起步准备 **2 台 VPS**：一台独立控制面，加一台应用服务器。每台应用 VPS 可以独立组成一个单节点 K3s 集群，不要求购买 3 台才能使用 Kubernetes。

| 主机           | 起步配置                                  | 推荐与用途                                                                                                 |
| -------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Oracle 控制面  | 2 核 / 12 GB / 80 GB                      | 足够作为本项目的起始预算；运行 Caddy、Console、API、Worker、平台 PostgreSQL/Redis，实际容量后续测量        |
| 应用 VPS       | 少量轻应用可用 2 核 / 4 GB / 60–80 GB SSD | 推荐 4 核 / 8 GB / 80–100 GB SSD，给 K3s、应用、镜像和小型数据库留余量                                     |
| 第二台应用 VPS | 按新应用需求选择                          | 需要多地区、独立故障域或资源不足时再增加；多集群验收的第二套可临时在本地建立                               |
| 独立构建环境   | Git/Dockerfile 自动发布需要独立 Linux Builder | 可先用可安全连通的本地 Linux VM；长期独立 VPS 以 2–4 核 / 4–8 GB / 40–80 GB SSD 为预算起点，大型依赖构建以实测调整 |

应用 VPS 推荐先用 Ubuntu 24.04 LTS、固定 CPU 架构，并具备 SSH 与所需 sudo 权限、稳定地址、镜像仓库出站连接。磁盘大小受数据库和持久卷影响，以上不是服务数量承诺；新建时保留至少约 20% 空间。构建不要与生产应用争用最后一点内存，Oracle 控制面不承担用户源码构建。

两台 VPS 可先承载控制面与应用，使用镜像发布。平台内 Git 自动发布还需第三个独立构建环境，但不必立即购买第三台 VPS：本地 Linux VM 在控制面可通过受控网络连通、且本机持续在线时可继续承担构建。普通 CI 自行构建和推送镜像后，也可以走平台的镜像发布路径；这不等于已经集成了平台 Builder 协议。当前安装与真实构建验证以 Ubuntu 24.04 ARM64 为范围，使用原生构建时 Builder 与目标应用架构应匹配；x86_64 或跨架构构建需要补齐对应安装资产和实际验证。

Oracle 的实际免费权益在控制台建机时核对。2026-10-26 再次读取的 [Always Free 官方说明](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)列出 A1 每月 1,500 OCPU 小时与 9,000 GB 小时，折合常驻 2 OCPU / 12 GB；用户账户可选择的 4 核 / 24 GB 仍需核对免费标识和费用预估。表中的应用 VPS 单独准备；若使用同一 Oracle 账户，需要合并核算所有实例的 CPU、内存与磁盘。

已有实例占用 50 GB、总磁盘额度按用户提供的 200 GB 计算，新控制面分配 80 GB 后余 70 GB；还要算保留卷等占用。无需因为最大可选计算规格更高就占满 150 GB 磁盘。

这套起步配置没有高可用保证。个人阶段通过异机备份降低数据风险；多节点高可用、数据库复制和跨地域容灾是不同的设计，不用增加一台服务器的数量来暗示已经具备。

## 接真实 VPS 时再提供

准备好后提供 SSH 配置别名或主机地址、系统/架构、CPU/内存/磁盘、是否已有 K3s，以及允许用于测试的范围即可。私钥、密码、kubeconfig 不发到聊天，使用本地受保护文件或已鉴权的凭证表单。平台先核对主机指纹和只读预检，再对明确的新测试目标初始化；已有集群走导入路径。
