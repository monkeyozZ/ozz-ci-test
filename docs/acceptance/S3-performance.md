# S3 性能验收

日期：2026-10-26。API 正常与 Redis 不可用两种场景各完成 600 秒测量；前端最终双窗口 600 秒复验达到本次交互目标，首次未通过的结果仍保留。生产 Linux 安装与真实云端容量另行验收，不能由这些测量推导整个 S3 或 Oracle 已通过。

## API 与 PostgreSQL

[正常场景原始结果](s3-api-load-available.json)和 [Redis 不可用原始结果](s3-api-load-unavailable.json)使用生产 Node 24 API、独立 loopback 端口和临时 PostgreSQL schema。M1 Pro、8 个逻辑 CPU、16 GiB、macOS；具体版本和采样时间在报告中。与主开发 API/Worker、Lima A/B 共用物理开发机，不施加 Oracle 的 CPU 配额，也没有公网往返时间。

样本为 100 个服务元数据、1 万条明确标注的失败部署历史、20 个项目与 40 个环境。服务通过真实 API 在模拟的集群身份上创建；历史直接写入仅用于测量的 schema，不投递也不启动应用。5 个闭环客户端持续 600 秒，混合列表、详情、revision 修改和最多每客户端 20 次诊断任务接收。该 schema 没有 Worker，任务执行/恢复另有真实产品证据。

| 指标 | 正常场景实测 | Redis 不可用实测 |
| --- | --- | --- |
| 持续时间 | 600.01 秒 | 600.01 秒 |
| 请求数 / 错误数 | 296,164 / 0 | 324,593 / 0 |
| 平均请求速率 | 493.60 次/秒，仅此负载条件 | 540.98 次/秒，仅此负载条件 |
| 服务端整体 P95 | 23 ms | 21 ms |
| 服务元数据 PATCH P95 | 41 ms | 36 ms |
| 持久任务接收 | 100 次 202，P95 32 ms | 100 次 202，P95 32 ms |
| API RSS 峰值 | 410,779,648 bytes，约 392 MiB | 395,657,216 bytes，约 377 MiB |
| API 平均 CPU | 173.43%，100% 表示一核 | 188.29%，100% 表示一核 |

| 退出清理 | 独立 API 已停止，本次临时 schema 已删除 | 独立 API 已停止，本次临时 schema 已删除 |

延迟包括所有响应，没有去掉失败、慢请求或只统计成功样本。服务端日志与请求 ID 全量对应，未匹配条目为 0。CPU/RSS 只统计该 API，PostgreSQL/Redis/Worker/浏览器/驱动的资源不在这些数值内；连接数快照为整个数据库范围，不能当作单个 API 的连接池等待时间。

Redis 不可用使用只属于隔离 API 的拒绝连接地址，执行前确认 PING 不成功；共享开发 Redis 保持运行。它验证数据库持久接收通路，不宣称发生了真实 Redis 进程崩溃，也不替代已有 Worker/队列故障验收。两轮运行时间和同机后台负载不同，不能从第二轮稍快推导出关闭 Redis 会提升生产性能。

命令与清理范围见 [开发说明](../development.md)。5 秒预检只用于检查脚本与数据，不能替代正式持续时间。

## Console 与持续日志

真实有限 Pod SSE 的读取、暂停、切换与清理已有[常规浏览器报告](../../apps/console/tests/artifacts/s3-local-lab/browser-results.json)。长时前端压测使用生产静态资源、受控服务/历史响应和两路受控 SSE，故意将浏览器渲染能力与远端 Kubernetes/Registry 的速度分开。后端真实 SSE 仍保持 60 秒和 1 MiB 上限。

[首次 600 秒结果](../../apps/console/tests/artifacts/s3-performance/ten-minute-before-optimization.json)未通过体验目标：259 个可见反馈样本中 244 个在 100 ms 内，P95 114.4 ms；长行窗口会话 INP 估计 424 ms，CLS 峰值 0.1296。缓冲、截断、中文 IME 和连接/计时器清理检查通过，但不能因此把整份性能结果标为通过。

产品改为可视范围渲染，补齐短行缓冲上限，并固定日志结束状态区域的布局。分析还发现旧测试通过 Playwright binding 传递大对象，递归反序列化会影响页面主线程；最终 fixture 改为随机 loopback 端口的只读 HTTP 服务，让生产页面经过原生 fetch/JSON 解析获取相同的数据与分页。没有跳过慢样本、增加等待时间来排除首次交互，或降低日志生成频率。旧结果与最终结果的测试传输实现、同机后台负载不同，因此不把所有差值归因于单一产品改动。

[最终原始结果](../../apps/console/tests/artifacts/s3-performance/final-frontend-performance.json)的日志窗口为北京时间 **02:26:54.653–02:36:54.837**，实测 **600,157 ms**。同机 API 长测已结束，没有并行镜像构建；生产静态资源来自本地 preview，Chrome **155.0.8059.85**、1440 × 1000 CSS px、DPR 1、headless，无 CPU/网络节流。浏览器测试驱动为 Node 22.21.1，产品 API/Worker 运行时仍为锁定的 Node 24；驱动版本不是产品运行版本。

| 指标 | 最终结果 |
| --- | --- |
| 数据集 | 100 个服务元数据、10,000 条部署历史；服务/历史遵守 50 条 cursor 分页 |
| 双窗口持续日志 | 每窗口 10 次追加/秒；各 11 次有限连接，最长约 55.037 秒，每连接不超过 1 MiB |
| 本地交互可见反馈估计 | 259/259 个样本 ≤100 ms；P95 45.9 ms，最大 83.9 ms |
| 会话 INP 估计 | 最大 80 ms；目标 ≤200 ms |
| CLS | 最大 0.00895；目标 ≤0.1 |
| 实际缓冲峰值 | 200,000 UTF-16 字符、10,000 行、211,594 UTF-8 bytes，分别取两个窗口的峰值 |
| 实际渲染行 | 最多 41 个节点，复制仍得到完整缓冲文本 |
| 并行管理响应 | 每秒一批 5 个并发请求，共 3,005 个响应、0 错误 |
| 中文 IME | 20 次组词/提交检查通过，组词期 Enter/Esc 不导航或关闭弹层 |
| 清理 | 两个窗口退出后连接/计时器均为 0；强制 GC 后单窗口 heap 回收约 0.9–1.1 MiB |

日志产品当前保留 **200,000 UTF-16 字符与 10,000 行，先到者裁剪**。这是比 PRD 的 5 MiB 最大字节预算更严格的现有限制；本次实际峰值约 207 KiB，**没有跑满 5 MiB**，不声称验证过 5 MiB 长文本缓冲。后端单次 1 MiB/60 秒控制传输，前端更小的缓冲控制视图与内存，两者各自独立生效，裁剪有明确提示。

最终报告的 `feedback100ms`、`sessionInp200ms` 和 `clsPointOne` 均为 `true`。可见反馈使用真实输入到 DOM 条件与下一 rAF 的估计；Event Timing、实验室 CLS 和 renderer heap 不等于合成器呈现时间、公网 RUM 或整机 RSS。真实 API/K3s SSE 证据仍由常规产品流程提供，受控日志流不能替代真实后端验证。
