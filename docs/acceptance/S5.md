## 真实流程发现与修复

1. Kubernetes typed List 的条目可省略 `kind/apiVersion`。StorageClass 和 ReplicaSet 只在验证列表外层类型后补齐缺失类型，显式错误类型仍拒绝；普通 Pod 保持 ReplicaSet 归属，StatefulSet 使用自己的身份。
2. 可写 PVC 引用和挂载的 `readOnly:false` 会被 Kubernetes 省略。比较只对这两个字段按默认值归一化，显式只读和替换卷仍视为真实差异。
3. PostgreSQL JSONB 会调整对象属性顺序。卷关联比较按 PV 名称/UID、节点名称/UID 规范化，避免把相同数据位置误判为替换；真实身份变化仍拒绝。
4. Kubelet exec 会先发送只有通道号的空 stdout/stderr 帧。数据库检查接受合法空帧，仍要求有效终态、受限输出、超时和 TLS 校验，不能把空状态帧当作成功。
5. 首次数据库模板仅保存卷意图，页面曾把尚未创建的卷与异常的未知观察混为一类而阻止发布。页面现在结合服务/模板/数据库/卷的双向身份、未开始初始化状态、未建立的写入保护及无历史观察判断首次创建；已有写入意图、错误、漂移或身份不足仍阻止，并明确提示首次发布才创建卷。

上述修复有对应协议、真实 PostgreSQL 或浏览器回归。完整 `pnpm check` 通过 349 项主套件、39 项 Console 单元和 60 项手工工具测试；完整数据库集成 210/210，包含全部 33 项存储业务检查。最后的首次创建界面修复另通过 Console 生产构建、类型检查、39 项单元、15 项受控流程和 66 次主题/尺寸检查，全仓 lint/format 再次通过。OpenAPI 与生成客户端重新生成后哈希保持一致。

三类恢复从开始导入到正式数据验证分别耗时 16.305 秒、17.585 秒和 15.811 秒；这些是本地小型样本结果，不是生产 RTO 承诺。

S5 固定源码已捕获为 `s5-20261026T004406Z-5b4fee22`，共 649 个文件，归档 SHA256 为 `fb0d8402542cac614268789efe0ece0860d4bc1c25b7de51d59b8b969264e173`。Linux 交付只读取这份快照；后续 S6 工作区修改与文档状态更新没有进入本次镜像。四镜像与 Compose 结果见 [s5-deployment-results.json](s5-deployment-results.json)，构建后的交付报告不回填快照。

失联验收保留了[原 45 秒窗口的失败](s5-observation-local-results.json)及恢复证据。该窗口没有满足三类观察同时过期的条件。后续独立探针按真实策略区分错误与观察年龄，设置 115 秒窗口上限和 130 秒看门狗，实际暂停 44.002 秒后已因三类请求超时满足条件；当时观察年龄约 55–59 秒，未等到 90 秒。13 项真实检查证明错误导致观察过期及恢复路径，90 秒的纯年龄分支只有 7 项静态分类边界检查，不能称为本次真实失联已验证。产品阈值和原失败证据均未改动。更早的预检仅因 K3s 进程标题和解包路径差异退出，尚未发送暂停信号；探针修正后仍核对唯一进程、PID、启动时间、boot ID、执行路径及命令行哈希。此验收证明 API 失联与恢复，不等于整机掉电或多节点自动调度验证。
