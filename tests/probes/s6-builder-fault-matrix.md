These probes are prepared acceptance procedures. Compilation, lint and temporary-file tests do not establish that any Linux fault has passed. Run them only in the root-coordinated window after the real HTTPS/UI/Webhook path completes.

The entry point is `pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs <mode> [case]`. It reuses the existing HTTPS fixture configuration and authenticated production API. `prepare` creates seven dedicated branches and seven services with `autoDeploy=false`, plus one generic secret containing a random canary with no external authority. It never starts a build. Every `start` creates a fixed-commit preview and uses the production deployment command; the probe never inserts a BuildRun, grants Builder credentials directly, or fabricates a closure or artifact.

The fixture main ref, original seed working tree, product state, provider state and Webhook state are hashed before and after each command. The local fault state and private receipts live under `.local/local-lab/s6-builder-faults`. Original Git history, deployments, artifacts and failed attempts remain in place. The Webhook completion guard requires `publish-pending`, `new-https-content` and the final `running-duplicate-stable` checkpoint. This matters because its baseline expects only one service on the shared repository before that acceptance finishes.

After the timeout observer hit the existing 10-login-attempt/15-minute limit, the probe gained a private `auth-session.json` cache (mode `0600`) bound to this fault session. Later commands validate the saved session with `GET /api/auth/me` and reuse it. Cookies and CSRF tokens never enter evidence or console output. Product login protections and rate-limit records are unchanged.

This plans seven scenarios and eight explicitly requested deployments. Observed failures can require further explicit retries; all attempts and failed receipts remain in the final inventory. Normal product retry policy can add runs inside a deployment; every such run must have a verified closure. PID, disk and memory pressure are separate so one exhaustion cannot hide another result. The source workload stops itself within 150 seconds even if an intervention is missed; no case intentionally waits for the normal 1,200-second deadline.

The local filesystem must retain at least 8 GiB free. Preparation requires 9 GiB; starting or retrying a deployment requires 10 GiB, reserving 2 GiB above that floor. The Builder guest must have at least 1.5 GiB free before starting a new execution. During observation and trigger waits, falling below 9 GiB locally requests cancellation of that exact fault deployment and records the measured space. Completion checks the 8 GiB floor again. The probe creates no VM, prunes no data, and never restarts the A/B K3s or Pebble services. Workload writes stay inside the existing 1 GiB loop filesystem; the 2 GiB workload cap is a finite attempt bound, not a relaxed quota.

Prepare once after the coordinated window opens:

```sh
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs prepare
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs status
```

For cancellation, `run-cancel` registers the deployment, then starts observation and cancellation concurrently in one authenticated session. The cancellation command waits for the controlled `cpu-complete` marker before making the API request. If the previous cancellation has verified closed runs and no artifact, it first registers an explicit retry and retains the old deployment ID in case history. This allows repeating an observation that missed the live interval without hiding the failed evidence. The first separate observer received HTTP 503 at login and missed the source; that attempt remains unaccepted for kernel isolation/CPU checks.

The API log at `2026-10-26T05:07:20.816Z` identified that HTTP 503 as `AUTH_BUSY`: the observer and cancellation processes submitted concurrent password checks to an API process that allows one Argon2id verification at a time. Root's read-only check found API/Worker healthy and no other contemporaneous warning. This was the probe triggering the existing login concurrency protection; it is not evidence of a Builder-induced control-plane failure. `run-cancel` avoids that collision without changing authentication limits.

```sh
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs run-cancel
```

For the short deadline, run these sequentially. The restore refuses open runs, changed backup bytes or unrelated intervening configuration changes. It restores the exact original bytes; it does not reinstall tools or restart a VM. If the manager died or restarted during the window, configuration restoration still succeeds and reports `managerRefreshRequired=true`; root must refresh the Builder manager and verify its signed limits before further runs because its cached admission limits may still be 40 seconds.

```sh
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs limits-begin
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs start timeout
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs observe timeout
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs limits-restore
```

The first timeout execution closed at its 40-second boundary but reported `BUILD_SOLVE_FAILED`: the launcher's whole-second `RuntimeMaxSec` calculation could stop a phase before its absolute deadline. The reviewed fix rounds the remaining duration upward to microseconds. After installing the exact reviewed launcher while idle, `timeout-retest-begin <launcher-sha256>` opens a new 40-second window with a fresh root backup UUID, preserving the original baseline and failed receipt. Run `retry-observe timeout`, then `limits-restore`; restoration uses that new window's backup. The final inventory records both the original host baseline and the authorized retest baseline, so the launcher update is explicit rather than being presented as unchanged.

For each of `pids`, `disk` and `memory`, run `start <case>` and immediately run `observe <case>`. Finish one case before starting the next; the Builder admits one execution group at a time. `retry-observe <case>` explicitly retries a closed failed/cancelled task with no artifact, preserves the previous deployment ID and immediately observes the new deployment. The PID case used this after its first sampler saw 256 tasks and source `EAGAIN` but no event in the parent slice. The retry captured the actual denial counter in the descendant building service (`pids.events max 21`); the initial incomplete observation remains a failed receipt.

For lost contact, run `start disconnect`, then `observe disconnect` in one exec session and `disconnect` in another. The control waits for the workload readiness marker, checks the selected deployment/run against the root ledger and pauses only the configured manager Node process in `ozz-builder.service`'s cgroup. The unit MainPID can be a `flock` wrapper; the controller selects its unique configured Node descendant and binds the guardian to its PID/start time/executable. After the original run acquires a verified product closure, the probe requests cancellation through the product API to bound any automatic retry. That cleanup cancellation is explicitly part of the receipt; it is not represented as an automatic task outcome.

For artifact reuse, run these sequentially:

```sh
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs start artifact
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs observe artifact
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs registry-allow
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs retry-artifact
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs observe artifact
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs stop-artifact
pnpm exec node tests/probes/s6-builder-fault-local-lab.mjs registry-restore
```

On failure, retain the session state and receipts. Run `limits-restore` after the host and manager ledgers have closed every run, and `registry-restore` if the dedicated repository ACL was added. Both restore modes work without the product API or fixture HTTPS service: they validate the session's private backup and exact current/original hashes, and reject an intervening third-party change. They never overwrite a configuration whose hash is unexpected. Atomic writes use fresh temporary names, so an interrupted previous write cannot block a restore retry; its leftover file is retained. Host backups remain root-owned under `/etc/ozz-builder/s6-fault-limits-<session UUID>`; the original ACL bytes remain in the private `registry-before.json`. If the API is unavailable, ACL restoration can finish first; `stop-artifact` must still stop the dedicated service through the API when it returns. The manager-pause guardian operates independently of the caller and always checks PID start time before resuming it. No restore or cleanup action deletes a task, proof or artifact.

`observe` saves the product task before host inspection, checks all retained build logs against the known fixture credentials and canary, and records an explicit `passed` flag. A missing sample, missing resource event, absent source process, incomplete closure or failed assertion remains a failure; the script does not infer a pass from the requested limits. Kernel sampling is read-only and uses the existing `s6-builder-kernel-sample.mjs` with `--timeline-seconds=120`. Its receipt contains raw cgroup counters and observed `/proc` namespace/UID metadata. Workload markers are separately labeled controlled output; for example, a `ready` marker alone does not establish a process sandbox, and an `ENOSPC` marker is paired with filesystem observations.

`observe-saved <case> <kernel-report-path>` resumes API evaluation using a live sample already captured for that deployment. It accepts only a private report from the Builder evidence directory, matches the deployment/run identity, and checks the sampler source hash. This recovered the timeout sample captured directly while API login was rate limited; it does not create or infer new kernel observations.

The canary is intentionally written to the build log in split writes to exercise redaction. The observer refuses to save log content containing the canary, either half, known Git/registry credentials or private-key markers. It never prints raw credential files, environment values, cookies or passwords. The guardian and timeout/ACL controls are still unexecuted until an actual run receipt says otherwise.
